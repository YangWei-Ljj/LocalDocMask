# ADR-003：建立分层识别与多源融合仲裁，本地 LLM 仅作补充

- 状态：Accepted
- 日期：2026-10-26
- 决策者：架构组

## 背景

现状：识别以正则为主，辅以 Ollama 候选；`confidence` 仅在 GUI 显示，不参与门禁/分流；同一实体被 regex 与 ollama 同时命中时按入表顺序去重、无仲裁（`detection.py:36-38`）；OCR 分数被丢弃；无上下文判定。总控指令要求建立"高精度规则 → 上下文识别 → 本地 NER/LLM 补充"的分层体系，并对规则与模型冲突做仲裁、做置信度校准。

## 决策

识别管线按以下顺序组织（`recognition/` 包）：

1. **高精度规则（rule_based）**：具有明确格式特征的实体（身份证 + 校验位、手机、邮箱、银行卡 + Luhn、护照、固定电话、地址、编号）。这是高可信来源。
2. **上下文判定（context）**：对公司名等上下文相关实体，先生成候选跨度（保召回），再用上下文窗口（前后 N 字）与"泛指引用"判定做精过滤（保精度）。泛指（我们公司/有限公司/股份公司/集团公司/银行医院大学）归 SUPPRESS；真实专名保留。
3. **知识词库（knowledge）**：从文件加载白名单、黑名单、公开企业名、领域术语，给出强先验。
4. **本地 LLM 补充（infrastructure/llm）**：Ollama `qwen3.5:9b` 输出仅作候选（来源 `ollama`，低权重），不参与最终安全判定的自我确认。
5. **融合仲裁（fusion）**：
   - 按（类别, 归一化文本）合并多来源证据。
   - 多源一致 → 提升置信度；白名单且无高风险来源 → SUPPRESS；黑名单 → CONFIRM。
   - 规则与模型冲突：高精度类型以确定性规则为准；上下文类型出现分歧 → 降低置信度并转 NEEDS_REVIEW。
   - 对原始置信度做校准，得到校准分与风险等级，再按 ADR-002 输出三档处置。

## 安全边界

- 关键安全判定（是否残留、是否可导出）不得只依赖模型自我确认；必须由确定性规则 + 独立审计（`security/auditor`）+ 必要人工审批形成闭环。
- LLM 异常、超时、低质量 OCR、引擎结论不一致时，按"无法确定"处理：转复核或失败关闭，不自动放行。

## 后果

- 正面：误报与漏报可分别治理、可解释、可回归；模型只增强、不独裁。
- 负面：融合与校准逻辑需要标注集持续校正（见 evaluation 包）。
- 约束：校准阈值先以基线数据建立，不虚构统一通过阈值。

## 实现状态（2026-10-26 对账，不重写决策）

- 落地于 `recognition/`：规则 `rule_based.py`、上下文 `context.py`、词库 `knowledge.py`、融合 `fusion.py`、门面 `pipeline.py`。
- 文中"黑名单 → CONFIRM"对应枚举值为 `AUTO_CONFIRM`（`domain/enums.py`）；`CONFIRMED/DISMISSED` 是用户显式裁决后的终态，不要混淆。
- 校准实测口径：多源（规则/名单≥2）+0.05；仅 `ollama` 来源的非高精度类 -0.15 并转复核；LLM 补充文本截断 8000 字、候选置信度 0.55。
- 本地 LLM 路径在测试中以 mock/离线方式覆盖，真实 qwen3.5:9b 精度未实测（见 docs/feature_list.md）。
