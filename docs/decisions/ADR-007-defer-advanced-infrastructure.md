# ADR-007：不引入多 Agent / 向量 RAG / MCP / Redis / 消息队列 / Docker（按需记录）

- 状态：Accepted
- 日期：2026-10-26
- 决策者：架构组

## 背景

总控指令要求对多 Agent、RAG、MCP、向量库、微服务、Redis、MQ、Docker 等先论证"具体业务问题、简单方案为何不足、输入输出契约、集成方式、成本、失败处理、安全边界、验收用例与预期收益"，无充分收益则放弃，禁止为简历堆砌。RepoMind 确实使用了多 Agent、Milvus、MCP，但其业务（跨来源 GitHub 协作、海量非结构化知识检索、需要 replan 的工程决策）支撑这些组件。

## 逐项评估与决策

| 能力 | 评估 | 决策 |
|---|---|---|
| 多 Agent 编排 | LocalDocMask 是确定性、顺序明确的流水线（解析→识别→上下文→融合→复核→脱敏→独立验证→导出），现有编排即可表达；"质量审计"已由确定性独立审计承担。多 Agent 重复调用模型只增加成本与不确定性，无明确可验证收益。 | **不采用**。保留单一确定性流水线 + 一个可选的 LLM 上下文判定角色（非多 Agent 系统）。 |
| 向量 RAG / 向量库 | 白/黑名单、公开企业名、领域术语规模小、以精确/词典匹配为主，简单文件方案足够；向量化会引入索引一致性、维度契约、运维成本。 | **不采用**。使用文件型知识（`resources/*.txt`）+ 精确/模糊匹配。 |
| 本地 embedding 模型 | 已安装 `qwen3-embedding:4b`，但不做向量检索即无使用场景。 | **暂不使用**，文档注明"已安装、当前未使用"。 |
| MCP | 本地单机桌面应用没有真实的 MCP 工具消费方；MCP 还可能成为绕过本地权限的通道。 | **不采用**，记录原因。 |
| Redis / 消息队列 | 桌面端以 QThreadPool 做有限并发，任务量小；引入外部中间件破坏"本地优先、零运维"定位。 | **不采用**。 |
| 微服务 / Docker | 与"本地优先、单机桌面"定位冲突。 | **不采用**。 |

## 复核条件

若未来出现以下情形可重新评估并走完整论证：需处理海量非结构化领域知识且文件匹配不足（再议 RAG）；任务复杂度需要动态 replan 且确定性流水线无法表达（再议多 Agent）；出现可信的外部工具消费方（再议 MCP）。

## 后果

- 正面：技术复杂度与真实收益匹配，体现"克制"的工程判断力；降低运维与攻击面。
- 负面：简历不堆砌这些名词；以确定性、可验证、安全闭环作为核心亮点。
